# Телеметрия: контракт аналитики v2

`Telemetry` — внутренняя шина игры. `ObjectivesSubscriber` использует подробные `RunStatsBatch.delta` для заданий. `AnalyticsReporter` перед отправкой переводит события через `toAnalyticsEvent` в отдельный контракт `AnalyticsEvent`. Изменение экспорта не меняет начисление прогресса заданий.

## Что отправляется и зачем

| События | Параметры помимо общего контекста | Вопрос аналитики |
| --- | --- | --- |
| `app.opened`, `app.ready` | тип запуска и язык при открытии | запуски, доля загрузившихся, время загрузки |
| `app.backgrounded`, `app.foregrounded` | без дополнительных параметров | уходы в фон и возвраты |
| `identity.linked` | предыдущая идентичность | связывание анонимного и платформенного игрока |
| `navigation.viewed` | экран, предыдущий экран / раздел при наличии | использование меню и конверсия в старт |
| `run.started`, `run.resumed` | уровень, сложность при старте; причина возобновления | старты и возвраты из паузы |
| `run.checkpoint` | причина, номер снимка, активное время, накопленные показатели | прогресс при паузе / уходе в фон |
| `run.ended` | причина, причина поражения, номер снимка, активное время, показатели, рекорд, `incomplete` | результат заезда, сложность, причины потери игроков |
| `economy.purchase_started/completed/failed` | товар; валюта и цена при старте/успехе; код ошибки при неуспехе | конверсия покупок и расход валюты |
| `reward.claimed`, `reward.failed` | источник, ID награды; состав, множитель, цикл/пресет при успехе; код ошибки при неуспехе | ежедневные награды, задания, колесо и компенсации |
| `daily.recovered`, `daily.recovery_failed` | день отката и цена / код ошибки | использование и стоимость восстановления |
| `ad.requested/opened/closed/failed/suppressed/rewarded` | место, формат; причина неуспеха/подавления либо ID награды | запрос → показ → закрытие, недоступность рекламы и выдача бонуса |

Общий контекст: `schemaVersion: 2`, `eventId`, `occurredAt` (UTC), `sessionId`, опциональный `runId`, `identity`, `platform`, `appVersion`. Язык передаётся один раз при `app.opened`. Дата сборки не дублирует версию в каждом событии. У `identity.linked` следующая идентичность уже находится в контексте.

`reward.claimed.rewards` описывает награды после выбора fallback: тип, количество/значение, валюта или ID и флаг `compensated`. Здесь нет полной конфигурации, вложенных fallback и UI-метаданных. Количество означает размер применённой награды; это не журнал изменений инвентаря с учётом вместимости боеприпасов/брони. Одно событие покрывает все награды одного получения. `rewardId` для дейликов — номер дня, для колеса — сектор (вместе с `presetId`), для заданий — ID задания/ступени.

## Показатели заезда

- `score`, `distance` (игровые кубы), `currencyCollected` (номинал golden/энергонов).
- `pickups` по типу: создано, подобрано, отклонено из-за заполнения, удалено без подбора. Это количество объектов: одна монета номиналом 5 golden — один подбор и 5 единиц валюты.
- Разрушенные препятствия по способу; выстрелы, попадания и попытки без патронов.
- Попадания по щиту, разрушения щита, активное время щита в мс.
- Начатые ручные прыжки и прыжки с трамплина.

Все показатели — накопленные за заезд. Для результата берите `run.ended`; для промежуточного состояния — последний `sequence`. Не суммируйте снимки одного `runId`. `durationMs` — активное время, без обратного отсчёта и пауз. `run.ended` с `incomplete: true` восстанавливается из последнего сохранённого checkpoint после перезапуска: это нижняя граница результата, а не полный финальный счёт. Его `runId` принадлежит исходному заезду.

## Что убрано из отправки

- `ui.action` и `ui.overlay_closed`: клики не дублируют фактическое открытие экранов.
- Отдельный `run.summary` и его обход очереди: итог представлен только `run.ended`.
- `batch.delta`, повторные верхнеуровневые score/distance и дублирующий `itemsRejected`.
- Подробные диагностические счётчики прыжков, промахов, видов препятствий и активаций щита. Они остаются во внутренней модели для заданий/отладки.
- Произвольные тексты исключений SDK: в экспорт попадают ограниченные коды, неизвестные причины обозначаются `provider_error`.

Подробный консольный журнал внутренней шины включается явно: `VITE_TELEMETRY_DEBUG=true` в dev-окружении.

## Доставка и ограничения

Одна очередь `telemetry.queue.v2`: максимум 500 событий, пачки по 50, отправка каждые 30 секунд и на ключевых границах жизненного цикла. При ошибке пачка остаётся в очереди с теми же `eventId`. Получатель должен удалять дубли по `eventId`: успешный адаптер может повторно получить пачку, если другой адаптер отказал. При переполнении вытесняются самые старые события. Подтверждение отправки удаляет конкретные ID, а не новые события, добавленные во время запроса.

Старая локальная очередь v1 не смешивается с новой схемой. Старые NDJSON-файлы остаются историческими логами прежнего формата; для их анализа нужен прежний контракт.

Сейчас в проекте настроены только DEV-адаптеры: консоль и локальный NDJSON endpoint Vite. Production-приёмника аналитики нет. При пустом списке адаптеров очередь не пополняется; внутренние подписчики заданий и рекламы продолжают работать. Для production надо подключить реальный `AnalyticsAdapter.track`, принимающий v2. Эта доработка не добавляет внешнюю передачу данных.

Проверки: `node --test tests/*.test.mjs`.
